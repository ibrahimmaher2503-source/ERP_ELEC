# ERP QA coverage matrix

Scope: current M01–M04 implementations and their shared workbook, audit, and demo-data integrations. This matrix records executable coverage that exists in the checkout, rather than treating a route or class as proof of working behavior.

Statuses use the campaign vocabulary: `PASS`, `FAIL`, `BLOCKED`, `NOT IMPLEMENTED`, and `NOT RUN`. The runner reports check-script results; it does not claim that every mapped scenario passed independently. `NOT RUN` below means no separate scenario-level result is available. Historical module receipts are distinct from this campaign. The runner emits a timestamped JSON report under `docs/qa/evidence/`.

## Contract resolution and limits

The owner resolved the Administrator policy conflict on 2026-10-21: Administrator receives every registered permission, including M04 Sales Order keys. Branch scope, active/verified identity, role membership, and domain readiness still apply. The Sales Order regression check now verifies both that the registered permission is synchronized and that access stays denied without branch scope, then succeeds only for the explicitly scoped branch.

The existing checks exercise stale versions and replay/idempotency sequentially, but they are not a multiprocess PostgreSQL race suite. No concurrency claim is made for official numbers, quotation allocations, reservations, delivery confirmation, invoices, or returns. Real successful inventory, accounting, delivery, accepted-quotation, issued-PDF, and return outcomes are outside current producers and remain blocked.
