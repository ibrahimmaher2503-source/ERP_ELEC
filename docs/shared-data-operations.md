## Contract

- Bulk selection consists only of explicit IDs, max500. Select-visible affects the current page; selections survive paging and can be cleared. No implicit all-matching mutation exists. Product operations allow status/category/brand/model/descriptions only. Each field explicitly keeps, sets or clears where permitted; empty is not clear. Normal Product Actions validate current references/versions, permissions and audit before/after values.
- Import supports create-only or update-existing by canonical SKU, never implicit upsert. Blank update cells keep existing values; literal #CLEAR clears only optional supported fields. Identity/base-unit/tracking/conversion rules remain unchanged. Unknown category/brand/unit codes fail rather than create masters. Duplicate SKU/barcode rows in one workbook are invalid.
- Template-first wizard: download the official entity/version template, upload .xlsx, inspect per-row preview, explicitly confirm, inspect persisted results/download report. Templates have Data/Instructions/Lookups and protected hidden _erp_template metadata, technical keys, Arabic labels/instructions, frozen headers and dropdown assistance. Metadata identifies compatibility, not authenticity or authority. Every execution reauthorizes the actor and normal domain actions.
- Private XLSX upload max10MiB,500rows; ZIP expansion max30MiB/1000entries; required sheets and exact headers/version validated. Formulas/macros/external links are rejected, never calculated. Export uses authorized database-side all/filtered/selected choices, lazy chunks and disk cell cache, explicit string binding prevents formula injection. One export max10,000rows; exceeding it fails rather than silently truncating.
- Migration080 creates technical run/item receipts and registers M02.product_bulk_update/import/export/template company-scope capabilities. No existing role gets automatic grants. Each operation additionally needs ordinary view/create/update/status permissions for actual effects. New capabilities are configured through normal dynamic RBAC.
- A preview only persists receipt plans, not Product changes. Each row executes atomically with its success marker. Duplicate confirmation/job delivery cannot repeat a committed mutation; stale versions and revoked grants fail rows without partial writes. Processing uses50-row jobs in the dedicated data-operations queue. Successful/failed/skipped counts reflect stored results, not client estimates.
