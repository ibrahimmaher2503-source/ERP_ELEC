## Shape and security

Each interface is `App\Modules\<Owner>\Application\Contracts\<Owner>Api`. Public request/result classes live beside it, named `<Method>Request` and `<Method>Result` in PascalCase. Public method names below are camelCase and take exactly one corresponding readonly Request, returning one readonly Result. No Eloquent or foreign Domain objects escape. Requests contain typed scalars/public value arrays; quantities/money decimal strings and IDs int, command UUID string. Domain functions receive their own scalar inputs, never import a foreign DTO.

Every mutation includes `actorId, branchId, commandId, correlationId, expectedVersion?` plus listed fields; actor comes from authenticated session/job context, never arbitrary browser payload. Every owner revalidates current actor scope and its invariants. Callers validate their owned source before constructing its immutable snapshot. Snapshot is not a bypass: receiving contract accepts only documented source module/type, command purpose and mandatory source version/ID; entry route never exposes an internal trusted-snapshot command directly. Query includes actorId/scope/filter/page; no global unscoped list. All mutation results include resourceId/status/version plus listed effect references; caller returns committedAt only after outer commit. No collaborator independently commits. Errors: Forbidden/NotFound/ValidationFailed/InvalidState/Conflict/InsufficientStock/PeriodClosed/IncompleteSetup. Return field errors for validation, 409 equivalent for stale/conflict, no secret/raw SQL message.

Optional means explicitly nullable, not arbitrary omitted mandatory data. Every query paginated max100 except fixed explicitly authorized posting source-line sets max500. Files return authorized internal references, not permanent public URLs. Public contract changes are integrator-controlled, versioned together with callers and tests. No alternate PublicApi tree.

### P02 executable foundation — contract 2.0

The 17 `OwnerApi` interfaces and final readonly method-specific Request/Result classes live in `app/Modules/<Owner>/Application/Contracts/`. Their promoted scalar properties and explicit PHPDoc array shapes concretize the payloads above. The [method inventory](../../tests/Fixtures/public-methods.json) covers the owner table, preparation APIs, master queries, imports and System conversation/intent contracts:160 methods. This inventory is test data, never a runtime dispatcher. No generic business payload class or alternate API tree exists.

Query context is `actorId, scopeBranchId, warehouseIds, requestedFields, filters, page, pageSize`; selected scope never grants access. Reporting additionally receives selected `branchIds`. Mutation context is `actorId, branchId, commandId, correlationId, expectedVersion` (explicitly nullable). Preparation APIs carry actor/branch/command/correlation plus their documented version/lock inputs. Constructors check positive actor/branch, UUID command/correlation format, positive provided version, query `page >= 1`/`pageSize=1..100` and max500 posting lines. Payroll.lockPayrollLines additionally requires a nonempty list of at most500 distinct positive integer lineIds, preserves caller order and returns owner ValidationFailed/lineIds on malformed sets; this does not establish authorization or lock eligibility. They preserve decimal strings. Owner actions must still validate nested keys/types, decimal precision/sign, dates, source/state/evidence/current grants and redact output. DTO construction is neither permission nor business eligibility; real validation and effects remain the producer cards.

Each owner publishes local `ErrorCode` and `ContractException` with safe messages/field errors, without a Shared dependency or Organization→System edge. HTTP-equivalent codes:Forbidden403, NotFound404 (also hidden records), ValidationFailed422, InvalidState/Conflict/InsufficientStock/PeriodClosed409, IncompleteSetup503. Future presentation adapters translate them; no business HTTP endpoints exist in P02.

The sole [ModuleServiceProvider](../../app/Providers/ModuleServiceProvider.php), registered in [bootstrap/providers.php](../../bootstrap/providers.php), maps all17 owners and records the unchanged exhaustive DAG. Every unimplemented binding throws owner `IncompleteSetup` on resolution in every environment; no fake implementation or success. Producer cards replace their binding explicitly before consumers run. Interface presence does not satisfy an actual producer dependency. P02 checks current references and negative fixtures/acyclicity; P03 provides full architecture/static enforcement.

Inventory receive/issue/reserve lines carry their own `sourceLineId`; results carry per-line qty, immutable costValue and movement/unit references. Multi-item custody intake returns each item/repair/holder. Invoice lookup returns invoiceLineId and immutable line net/tax/gross amounts for source-owner corrections. Payroll adjustments retain separate absence/rest-holiday components. None authorizes foreign model/ledger reads.

System command snapshots use `{resultType,contractVersion,canonicalJson}` to preserve the full owner Result losslessly. This is an opaque technical receipt: operation→result type is a fixed reviewed mapping, never a class supplied by the user or reflection dispatch. The owner validates/reauthorizes before replay; System stores/returns the bounded canonical JSON without importing consumers. Staged rows similarly return schemaVersion/entityType/canonicalPayload, retaining nested import data; root Cutover selects the fixed owner mapping, decodes and validates it. Future producer validators cap canonical payload/result JSON at256KiB per record, permit nested arrays/objects containing scalar/null values, reject PHP objects/resources/non-finite numbers and retain decimals as strings. Owner entry payloads remain their concrete typed shapes. No arbitrary JSON creates executable instructions.

Server-only intent reads/claims return saved canonicalPayload, sourceVersions and stable operation/command/hash for current revalidation. A purged terminal payload is null and cannot execute. Conversation reads include request identity, safe record references and durable execution bindings; consequential bindings contain intentId only, never a copied consequential payload. Root reauthorizes/redacts before any provider-facing projection; these internal reads are never tools. Persistence/encryption/expiry/recovery execution remains AI-R02 and owner cards.

Mutation Results remain provisional until the outer coordinator commits; none adds committedAt. Lock contracts require the same already-open default PostgreSQL transaction and return transaction-local opaque metadata, never DB/model handles; the owner implementation rejects calls outside it. No independent commit/network under locks. P02 opens no transaction and cannot prove atomic posting; later real integration/concurrency acceptance remains required.

AI-R01 foundation consists only of provider-neutral readonly [OperationDescriptor](../../app/Application/AI/Contracts/OperationDescriptor.php), [OperationRequest](../../app/Application/AI/Contracts/OperationRequest.php) and [OperationResult](../../app/Application/AI/Contracts/OperationResult.php). No executor, callable registry, provider or AI route is enabled. Concrete closed schemas, permission/preview/action/parity tests arrive with owner cards before AI-R02 registration; internal collaboration APIs are never automatically tools.

## Approved coordinator boundaries

1. Goods sale: **Sales** begins command/transaction → locks source/period/exposure/stock in global order → DeliveryReturns creates/confirms physical document → Inventory issue/COGS → Sales posts invoice or releases existing deferred revenue → AR item/GL as needed → outbox/audit/command receipt → commit. Inventory owns inventory journal through Accounting; Sales must not post COGS again. Invoice-only before delivery posts deferred revenue/VAT and AR, zero stock.
2. Purchase receipt: **Purchasing** → Inventory receives and posts Dr Inventory/Cr GRNI once → Purchasing receipt record/command result. Supplier invoice: Purchasing → AR/AP+Accounting clears GRNI/input VAT and creates AP; Inventory cost adjustment only via its owner when policy allows, not double inventory debit.
3. Trade returns: Sales/Purchasing validates commercial eligibility and approval → DeliveryReturns owner records return and physical Inventory effect → original coordinator posts credit/AP/AR/revenue/tax effects → corrections preserve original links. Inventory posts customer stock/COGS reversal or supplier-return clearing/Inventory entry; commercial coordinator must not duplicate it.
4. Contract billing: **ServiceContracts** locks eligible contract source → Sales.postExternalServiceInvoice receives trusted source snapshot → AR/GL → Contracts records allocation. Invoice correction starts **ServiceContracts.correctContractBilling**, not generic Sales edit; it updates eligibility and invoice/GL once. Noncontract service corrections enter the owning service coordinator analogously.
5. HR/payroll: **Payroll** validates employee/source → Attendance owner stores time/leave/advance/recovery → Treasury/Accounting as appropriate. Payroll coordinates advance disbursement; Treasury records cash with payroll-owned posting plan, no second salary journal. Employee snapshot is built from Payroll-owned persisted data, never accepted from browser. Attendance validates its own state/scopes and cannot call EmployeeLookup back.
6. Custody: WorkshopRepairs owns holder version lock and movements. Its parts use Inventory; its billing uses Sales or Contracts. Inventory cannot query jobs, Sales cannot query repairs, Contracts cannot query service modules back. Required customer evidence already persisted by source owner.

## Posting-purpose allocation and correction

Inventory `receive` with purpose purchase_receipt owns Inventory/GRNI; `issue` sale_delivery owns COGS/Inventory; `issue` service_part owns ServiceParts/Inventory; count owns InventoryVariance. Internal transfers own no entity GL change; movement location/value facts still immutable. Sales owns revenue/deferred/VAT; Purchasing owns AP/GRNI clearing and price variance; Treasury owns cash/AP/AR on ordinary trade money; Payroll owns salary/advance/payroll-liability plans even where Treasury supplies the money movement. Passing `postingPlan` to Treasury is restricted to these named caller types and balanced account-role templates, never arbitrary user-supplied GL lines.

Partial source reversal consumes remaining reversible quantity/amount. Customer returns and service-part returns reverse original exact tax/cost snapshot, not current profile/average. Supplier returns are the explicit exception: current moving average with separate price variance, as below. A later sale/return/paid allocation is a dependency that must be resolved by its owner's approved correction flow. New source identity does not bypass cumulative reversal limit. Cases AT-07/08/09/12/14 verify.

Supplier credit net N/inputVAT T against returned stock cost C: Purchasing posts DrAP N+T, CrInputVAT T, Cr1108 C, plus Dr5106(C−N) when C>N or Cr5106(N−C) when N>C. Supplier return physical and commercial credit are mandatory atomic V1 effects; no uncredited supplier dispatch. Customer return to paid invoice produces refundable credit; Treasury refund posts DrAR/CrCash (supplier refund receipt DrCash/CrAP) and settles that credit once. Excess credit use on another invoice has no cash/GL effect because the original credit already affected the control account.

When not wholly eligible: Inventory leaves pool unchanged; Purchasing clears original GRNI and posts whole D to5106. Negative delta must not make pool value negative; reject impossible invoice input. Source/purpose keys protect adjustment replay.

### Required transaction-only preparation APIs

`Accounting.lockPeriod(date, mode=posting/closing)` returns opaque transaction-local periodLockToken; posting uses shared row lock, closing exclusive. `Parties.lockCreditProfile(partyId)` returns current profile under party row lock; `ReceivablesPayables.lockPartyBalances(partyId, side)` serializes all exposure/allocation changes for that party/side and returns current totals. These serialize invoice posting, cash allocation, credit changes and credit notes; no cached exposure allowed.

`Inventory.lockStockPlan(lines(productId,warehouseId,binId,condition,serialIds), source, periodLockToken)` creates/locks valuation pools in ascending product order then balance/unit rows in ascending keys and checks freeze. `Treasury.lockMoneyPlan(accountIds,paymentIds)` and `Attendance.lockAdvancePlan(advanceIds)` acquire the later money/advance rows in ascending order. `Payroll.lockPayrollLines(lineIds)` protects payout/recovery eligibility. Each document-owning module exposes `lockDocument(documentType,id,expectedVersion)` for only its documented source types; nested coordinators supply validated snapshots after owner lock. Queries never expose these lock tokens to browser; calling outside same open transaction fails. Methods return primitive snapshots/token metadata, never model/connection handles. Owner actions verify their required locks and may idempotently reacquire already-held locks; they never acquire an earlier tier after a later tier.

Sale sequence: command → Accounting.lockPeriod → Parties.lockCreditProfile + AR.lockPartyBalances → Sales local source lock and DeliveryReturns.lockDocument when existing → Inventory.lockStockPlan → Treasury.lockMoneyPlan for consumed prepayment → owner postings → sequence/outbox/complete. Purchase receipt: command → Accounting.lockPeriod → Purchasing local PO/receipt lock → Inventory.lockStockPlan → Inventory receipt journal → source/sequence/outbox. Supplier invoice/return adds party/AP tier before document/stock tiers. Payroll obtains period before source/payroll/advance/money tiers. Root ClosePeriod obtains exclusive period before reconciliation. Two opposite-operation transactions and close-vs-post must finish without reverse-order deadlock; at most3 same-command deadlock retries remain required.
